# Service status

Settings → Status is the monitoring destination on web and Android. Connections manages calendar feeds and credentials; About contains app information. A dashboard warning links directly to Status when sources need attention or their status cannot be checked. Recommendation-specific context and parsing warnings remain available in the advanced recommendation explanation view.

Both relay targets return the same `GET /v1/health/sources` policy. The response includes human-readable source names, the latest attempt, `last_success_at`, data age, retry state, a source condition, a monitored-source summary, and runtime details. Weather participates through its saved forecast and latest attempt. Health assembly reads saved telemetry; on an automatic local relay or Worker, dashboard and Status reads also queue eligible recovery work in the background. Manual local relays keep reads passive. Web and Android Status offer **Refresh sources**, which explicitly requests upstream updates through `POST /v1/poll` and then reads the results. Android pull-to-refresh in Status uses this action too.

Freshness and update failures are separate facts. `freshness` is `live` through one expected update interval, `ageing` after one through three intervals, `stale` after three through six, and `dead` after six. Dead means saved data is too old to rely on; it does not mean the source is permanently gone. Weather overrides the stale/dead windows to 60/180 minutes. `condition` keeps the existing client-compatible health and failure labels. A recently failed attempt can therefore have condition `failing` and freshness `stale` together.

Each row also provides `recovery: { state, action, next_attempt_at, automatic, reason }`. This distinguishes an active update, a scheduled update, a retry waiting for provider backoff, an overdue update, missing configuration, an unused source, and a relay with automatic polling disabled. Public job metadata includes last outcome and lease expiry without exposing the lease token.

Configured sources without a successful check are unknown. Successful empty feeds are healthy. Partial parses and failed or implausible attempts need attention. Freshness follows successful data, so a recent failed attempt never makes old data look new. Default source thresholds use the shared age ladder; weather follows its forecast cache thresholds of stale after 60 minutes and dead after 180 minutes. Clients age status locally between checks, and failed checks visibly label cached telemetry as last known information.

Automatic polling reconciles missing schedules before selecting work, repairs overdue legacy schedules and interrupted claims, and checks eligible sources in the same pass. Failures in one source do not stop the others. Partial parses and skipped stale menu renders receive recovery attempts instead of being treated as complete successes. Transient retries start around 30 seconds and back off to a 15-minute probe window; persistent failures keep probing. Authentication, implausible responses, provider minimum intervals, and HTTP `Retry-After` may require longer waits. Google Calendar respects a six-hour minimum refresh interval and longer rate-limit cooldowns. Manual refresh also respects these protections and reports waiting sources rather than claiming they all updated.

Recovery keeps the existing lease and storage generation fences: an expired or superseded run cannot replace a newer result. Worker polls remain capped to fit the D1 query budget, leaving remaining sources due for later ticks. Disabled, unconfigured, and duplicated Google subscriptions are excluded from automatic work. A corrupt weather cache is repaired on its next permitted provider attempt. Missing credentials and malformed upstream data may still require user or provider action; automatic recovery does not invent replacement data or change private feed URLs.

An unused optional feed or alternative schedule connection is excluded from totals. Two entries using the same Google Calendar subscription count as one monitored source. Each visible row still explains whether its connection is in use.

Runtime information describes the backend that answered, rather than inferring deployment from the browser hostname. Local relays expose process uptime and whether polling is automatic or manual. Cloudflare Workers expose scheduled polling and current isolate age. Isolate age is not an availability or uptime percentage. Historical service availability is not measured by this endpoint.

Regression tests cover failed attempts preserving successful-data age, configured but unchecked sources, valid empty feeds, alternative and shared connections, cached weather failures, local status ageing, D1 receipt parity, and Worker runtime reporting.
